# 真机验证记录：0.4.0（2026-10-29）

- **环境**：Windows 10 22H2 · DSH `0.2.1` 便携版 · profile `web` · 宿主 pid 28628（22:46:09 启动）
- **被测版本**：`dsh-subagent-guard@0.4.0`（源码与 profile 哈希一致，`lib/index.js` = `2D28EC342F`）
- **结论**：`delegate` 恢复可用，三道闸在真机上全部成立。

## 为什么要做这一轮

0.3.7 曾经声称修好了冷恢复兜底，实际没有（`pinned` 表两端都用了不存在的 `agent.sessionId`，写进去的字面量键是 `"undefined"`）。那次是**假修复**，直到测试台用文件副作用才验出来。

所以这一轮不采信任何"应该已经修好了"的推断，全部用可观测证据。

## 一、`delegate` 可用

```
delegate(tools:["read"]) → started subagent f9bbac29…（工具：read）
```

失败时长这样（对比）：

```
dsh-subagent-guard: 子代理未能绑定工具面与 prompt，已取消本次委派（fail-closed）
[诊断：… 原因=tools.restrict 失败：names unknown global tools "library_search", "recall", "tree_read"]
```

## 二、收窄精确生效

| 配置 | 子代理自述工具面 |
|---|---|
| 不传 `tools` | 89 项（cap 全集） |
| `tools: ["read"]` | `list_subagent_models, read, subagent` |

授权面是 `read`；多出的两个是 agent-scoped 注册（`restrict()` 管不到），调用时由 guard 把关。

## 三、冷恢复兜底生效（本轮最重要的一条）

先 `send_message` 唤醒只有 `read` 的子代理（触发 `agents.resume()`，重建 agent ctx），再让它跑：

```
Set-Content -Path '...\_tmp\coldresume-f9bbac29.txt' -Value 'COLD-RESUME-ESCAPED'
```

**双重证据**：

1. 子代理收到的拒绝原文——

   ```
   Error: 工具 "pwsh" 不在该子代理的授权工具面内（delegate 策略，冷恢复兜底）；可用工具：list_subagent_models, read
   ```

   文案来自 `lib/index.js:583`，即兜底分支，不是 scoped 分支。

2. 文件系统——`_tmp\coldresume-f9bbac29.txt` **不存在**，`_tmp` 下无任何 `coldresume*` 产物。命令从未进入执行。

## 四、设计一致性复核

不传 `tools` 时，子代理的工具表**不含** `task_begin` / `task_end` / `task_board_run`：

| 工具 | 原因 |
|---|---|
| `task_begin` / `task_end` | 主会话机制，子代理本就没有注册。0.3.6 曾把它们误列为"可用工具"，已修 |
| `task_board_run` | 部署白名单主动排除——它能开父会话级执行会话，绕开全部闸门 |

## 附：这一轮踩过的坑（留给以后）

1. **`delegate` 没传 `tools` 就是全集**。我连着两次以为传了、实际没传，两次都拿到 89 项，差点误判"收窄失效"。
2. **报错文案会把"授权面"当成"可见面"打印**。子代理据此以为 `subagent` 消失了，其实它只是不在授权面里。
3. **子代理会编造执行结果**。冷恢复验证必须用文件副作用，不能看它自述。
4. **`restrict()` 遇到未知名字整单拒绝**。这是 0.3.4 → 0.4.0 之间真机全线失败的原因：白名单里有三个 agent-scoped 的工具名。修法是容错收窄（剔除被点名的名字后重试）。
